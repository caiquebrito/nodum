# 036 — Extend NodeType with struct/enum/protocol/extension

## Status: done

Implemented and tested (6 new cases across `graph-gen.test.ts`, `graph-diff.test.ts`,
`handlers.test.ts`; full workspace suite green — 275 core, 95 cli, 60 mcp, 8 benchmarks, 438
total, up from 432 before this spec — and every pre-existing test passed unmodified, confirming
no stats literal anywhere needed updating). Real check: synced a real TypeScript fixture (an
interface, a function, and a class implementing that interface) with the real CLI, inspected
`graph.json`, diffed a re-sync against the original with `nodum diff`, and confirmed the MCP
`search_graph` handler accepts the new `type_filter` values without error — see Success Metrics.

## Goal

Widen the graph's node vocabulary from 5 types to 9 (`struct`/`enum`/`protocol`/`extension` new)
**before** either the Swift or Objective-C parser exists (specs 037/038), so neither ships a node
type it would have to re-type in a follow-up spec. Update every place that semantically — not
type-checkingly, since there is no exhaustive switch/`Record<NodeType, …>` anywhere in this
codebase, confirmed by a full sweep — depends on the previously-closed 5-member set.

## Why now

First of the four specs in the v2.7.0 "iOS: Swift + Objective-C" batch. Swift's grammar folds
`class`/`struct`/`enum`/`actor`/`extension` into one `class_declaration` node type, and neither
Swift's `protocol` nor Objective-C's `@protocol` maps cleanly onto the existing `'interface'`
type (similar concept, not identical — keeping them distinct avoids conflating a Java `interface`
node with a Swift `protocol` node in a project that mixes languages). Batching this ahead of the
two parser specs, per the plan's Decision C, avoids re-typing churn — the alternative (shipping
037/038 against the old 5-type set, then widening it) means shipping and then changing a public
type in back-to-back releases for no reason.

## Scope

- `NodeType` in `packages/core/src/types.ts` gains `'struct' | 'enum' | 'protocol' | 'extension'`.
- `Graph['stats']` gains four **optional** counters: `structs?`, `enums?`, `protocols?`,
  `extensions?` (Decision A — see Design).
- `buildStats()` in `packages/core/src/graph-gen.ts` always populates all nine keys on any graph
  generated after this spec, regardless of whether the project has any Swift/ObjC code.
- `search_graph`'s `type_filter` enum in `packages/mcp/src/index.ts` gains the four new values.
- `handleGetGraph`'s stats/node-type breakdown in `packages/mcp/src/handlers.ts` gains four
  conditional lines each, rendered only when the count is non-zero — keeps a non-iOS project's
  output byte-identical to pre-spec output.
- `packages/core/src/memory/summary-builder.ts`'s `SUMMARY.md` generation gets the same
  conditional treatment.
- `packages/viewer/app.js` (**source copy only** — `packages/server/viewer/app.js` is a
  gitignored build artifact regenerated by `packages/server`'s own build step, never edited
  directly): `TYPE_COLORS` gains the four new types **and fixes a pre-existing gap** where
  `interface`/`method` already fell back to the generic grey; a new `CONTAINER_TYPES` set makes
  `nodeSize3D` treat the four new types as container-tier sizing like `class` (deliberately
  **not** including `interface`, to avoid an unplanned visual-size change to every existing
  TS/Java project); a new `TREE_ICONS` map replaces the old binary `class ? '◆' : 'ƒ'` tree-view
  icon logic with a per-type glyph.
- `packages/core/src/graph-diff.ts`'s `statsDelta` computation: fixed to treat a missing optional
  stat (a pre-036 `graph.json` diffed against a post-036 one) as `0` rather than `undefined`,
  which would otherwise produce `NaN` deltas — a real compile error surfaced this immediately
  (see Design).

## Out of scope

- Any parser emitting the new types — that's specs 037 (Swift) and 038 (Objective-C).
- `RelationType` changes — no new relation kinds in this spec.
- `normalizeNodeId()` changes. A same-file Swift `struct Foo` and `class Foo` would collide on id
  under the current name-only scheme (it ignores `type` for non-file nodes). Changing the id
  scheme to incorporate node type would invalidate every existing node id in every user's graph
  (and every incremental-sync cache keyed on those ids) — rejected. The collision is instead
  handled at the parser level in spec 037 via an explicit name-based first-wins dedup, documented
  there.

## Design

### Decision A — stats shape: optional keys, always populated (not required keys)

The two options considered: (a) required keys, semantically precise but forces updating every
stats object literal in the codebase; (b) optional keys, always populated by `buildStats()` on
any fresh graph, with old on-disk data staying valid because the fields are optional.

**Chosen: (b).** A grep sweep found **59 stats-shaped object literals across ~34 files** —
overwhelmingly test fixtures (`graph-gen.test.ts`, `graph-diff.test.ts`, `handlers.test.ts`, and
several more) — that would all need a mechanical four-key addition under option (a), for zero
behavioral gain (every one of those fixtures is testing something unrelated to the new counters).
Option (b) costs nothing at any of those sites; `graph-diff.ts`'s `statsDelta` already computes
generically over `Object.keys(b.stats)`, so it needed only the `?? 0` fallback described below,
not a rewrite. The tradeoff, stated plainly: the "breaking change" the roadmap calls for is real
in practice (every fresh sync gets the new counters) but not compiler-enforced — a hand-written
`Graph['stats']` literal without the new keys still type-checks. Confirmed acceptable given the
alternative's cost is pure mechanical churn with no test strengthened by it.

### The graph-diff.ts fix this decision required

Making the four new stats keys optional immediately surfaced a real `tsc` error in
`graph-diff.ts`'s `statsDelta` computation (`b.stats[k] - a.stats[k]`, now possibly
`number | undefined`) — exactly the kind of finding this project's spec process asks to be
verified and documented rather than silently worked around. Fixed by treating a missing key as
`0`: `(b.stats[k] ?? 0) - (a.stats[k] ?? 0)`. This is the correct semantics for diffing a
pre-036 `graph.json` (genuinely has zero Swift/ObjC nodes, not "unknown") against a post-036 one.

### Viewer: `interface`/`method` color fix is a pre-existing-gap fix, not new scope

`TYPE_COLORS` before this spec only had `file`/`function`/`class` — `interface` and `method`
nodes already silently fell back to the generic grey (`#6e7681`). Since this spec is already
touching `TYPE_COLORS` to add four new entries, the two pre-existing gaps were fixed in the same
pass rather than left as a known bug to revisit later.

### `CONTAINER_TYPES` deliberately excludes `interface`

`nodeSize3D`'s pre-036 behavior only special-cased `file` (largest) and `class` (medium); every
other type, including `interface`, got the smallest tier. The new `struct`/`enum`/`protocol`/
`extension` types are added to the medium tier (they're containers, like `class`) — but
`interface` is deliberately left in the smallest tier, unchanged from before, so this spec's
viewer changes don't introduce an unplanned visual-size change to every existing TypeScript/Java
project that already has interface nodes. Only new-to-this-spec types get new sizing behavior.
